  ★ Insight ─────────────────────────────────────
  This is a fundamental Rust distinction worth locking in: mutability is a 
  property of bindings, not types. In C++ you'd say const vector<Item> vs
  vector<Item> — the constness is part of the type. In Rust, Vec<Item> is always
   the type; mut is metadata on the variable name that the compiler uses to
  enforce local discipline. This is why mut appears on the left side of let, not

⏺ OK. Before writing any code, let's make sure the DP's job is crystal clear.

  Input: the Vec<Item> you just built — a sequence like Box Glue Box Glue Box 
  Glue Box.

  Output: a list of positions in that item stream where we should break into
  separate captions.

  The constraint: each caption's total character width (sum of box widths + glue
   widths between them) must not exceed some maximum — let's hardcode 37 for now
   (one line, single-level; we'll handle two-line captions later).

  The objective: minimize total "badness" across all captions, where badness
  measures how far each caption's width deviates from the ideal.

  ---
  First thing the DP needs to know: where are the legal breakpoints?

  Not every position in the item stream is a valid place to break. In
  Knuth-Plass, you can only break at a Glue item. You never break in the middle
  of a Box, and Penalty items modify the cost of nearby breaks but aren't
  themselves break positions (yet — we'll revisit when we add penalties).

  So step one is: scan the item stream and collect the indices of all Glue
  items. These, plus the start (before index 0) and end (after the last index),
  are your breakpoint candidates.

  For the stream Box₀ Glue₁ Box₂ Glue₃ Box₄ Glue₅ Box₆:

  Breakpoints: [0, 1, 3, 5, 7]
                ^  ^  ^  ^  ^
              start |  |  | end
                glue positions

  Breakpoint 0 means "before everything." Breakpoint 7 means "after everything."
   Breakpoints 1, 3, 5 are the glue positions where a caption boundary could go.

  ★ Insight ─────────────────────────────────────
  The convention is: breaking at a Glue means the glue gets consumed — it
  becomes the boundary between captions rather than a space within one. So if
  you break at Glue₃, caption 1 is Box₀ Glue₁ Box₂ (the words with a space
  between them) and caption 2 starts at Box₄. Glue₃ itself doesn't appear in
  either caption — it was "spent" on the break.

⏺ Good. Next: the two arrays.

  You need a cost and a prev, both indexed by breakpoint number — not by item
  index, by position in your list of breakpoints.

  For our example with breakpoints [0, 1, 3, 5, 7], that's 5 breakpoints, so
  both arrays have length 5.

  - cost[0] = 0.0 — it's free to be at the start.
  - cost[1], cost[2], cost[3], cost[4] all start at f64::INFINITY — we haven't
  found a way to reach them yet.
  - prev[0] doesn't matter (no predecessor). Initialize all of prev to 0usize.

  The DP will fill these in left to right. When it's done, cost[4] holds the
  minimum total badness for captioning all the words, and prev lets you trace
  back the optimal break sequence.

  ---
  Now the core question: what goes in the inner loop?

  For each breakpoint j (starting at 1), you look backward at every earlier
  breakpoint i and ask: "if I made a caption from the words between breakpoint i
   and breakpoint j, how wide would it be, and how bad?"

  For each candidate (i, j):

  1. Compute the width — sum up the widths of all items between breakpoints i
  and j. That means the Box widths (the words) and the Glue widths (the spaces)
  that fall between those two breakpoints.
  2. Check feasibility — if width > MAX_WIDTH, this caption doesn't fit. Skip
  it. And since adding more words only makes it wider, you can break out of the
  backward scan entirely.
  3. Compute badness — for the skeleton, use (MAX_WIDTH - width)² as a float. A
  perfectly full line has badness 0. A short line has high badness.
  4. Update — if cost[i] + badness < cost[j], then this is the best path to j so
   far. Set cost[j] = cost[i] + badness and prev[j] = i.

  ★ Insight ─────────────────────────────────────
  The backward scan with early termination is the key to performance. You're
  iterating i = j-1, j-2, j-3... and accumulating width as you go. The moment
  width exceeds the max, every earlier breakpoint would produce an even wider
  caption, so you stop. For 37-character subtitle lines with average word length
   ~5 characters, each backward scan examines maybe 5–7 candidates before
  overflowing. That's what makes the practical runtime O(n · m) rather than
  O(n²).
  ─────────────────────────────────────────────────

  There's one tricky detail in step 1: "sum up the widths of all items between
  breakpoints i and j." The breakpoints are indices into the item stream.
  Breakpoint i sits at some item index, and breakpoint j sits at another. The
  items between them — exclusive of the break positions themselves — are the
  content of the caption. How would you iterate those?

   active nodes and trims from the front.

❯ What about `running_width`? Is that a kludge?                                 

⏺ It's doing real work — accumulating Box widths between Glue positions — but
  it's solving a problem that cumulative_width could solve on its own if you
  tracked it differently.

  Right now you have two accumulators: running_width (reset at every Glue) and
  cumulative_width (stored per breakpoint, built from the previous breakpoint's
  value + running_width + glue width). The reset-and-accumulate pattern works,
  but it means the cumulative value is only computed at breakpoint moments, not
  continuously.

  The simpler approach: keep a single running total that grows on every item —
  Box or Glue — and just snapshot it whenever you see a Glue:

  let mut cumulative_width: usize = 0;

  for (i, item) in items.iter().enumerate() {
      match item {
          Item::Box { width, .. } => cumulative_width += width,
          Item::Glue { width } => {
              cumulative_width += width;
              breakpoints.push(Breakpoint {
                  item_index: i,
                  cumulative_width,
              });
          }
          _ => {}
      }
  }

  One accumulator, no resets, no reaching back to the previous breakpoint's
  value.

  ★ Insight ─────────────────────────────────────
  This is a general pattern: if you find yourself resetting a counter and then
  adding its value to a running total elsewhere, you can usually replace both
  with a single monotonically increasing accumulator that you sample at the
  right moments. The reset was an artifact of computing deltas manually when you
   already had the information to compute the absolute value directly.
  ─────────────────────────────────────────────────

  This also sidesteps the breakpoints.last().unwrap() issue for computing
  cumulative width — you're no longer referencing previous breakpoints at all.
  You still need last() or similar if you want to verify anything, but the core
  logic doesn't depend on it.
