# Lexical spike --- evaluating Lexical as a Slate replacement

**Branch:** `lexical-vibes` (git worktree; the main tree is untouched).
**Verdict up front: MOVE TO LEXICAL.** All three litmus tests pass, and each one
maps directly onto a wall Slate hit. The one caveat is a backend gap
(`splitStatement`) that the split-on-Enter feature exposes but does not depend on
to demonstrate.

This document is organised as: what to run, then one section per litmus test,
then a running discoverability log, then the recommendation.

### A routing gotcha worth recording

The requested filename `interview.$interviewNumber.lexical.tsx` nests the new
route **under** the Slate route in TanStack's flat-routing tree. The Slate route
renders no `<Outlet/>`, so the child would never paint. The fix is TanStack's
trailing-underscore **de-nesting** convention: `interview.$interviewNumber_.lexical.tsx`
keeps the URL `/interview/:n/lexical` but re-parents the route to the root, so it
renders standalone and the Slate route stays untouched. The generator rewrites
the `createFileRoute("/interview/$interviewNumber_/lexical")` path token to match.

## Litmus test 1 --- EDIT LATENCY

**Slate's wall:** brutal keystroke latency even virtualized down to ~10 nodes per
page, *before any feature was added*.

**Root-cause hypothesis (the thing the spike tests):** Slate's `<Editable/>` is a
**controlled** React component. Every keystroke becomes an operation that
round-trips through React: Slate re-renders the element tree, and the cost scales
with how much of that tree React must reconcile. Virtualization is a band-aid ---
it shrinks the tree React sees, at the cost of the complexity you saw in
`TranscriptElement` (a `useVirtualizer` wired to the playhead).

**Lexical's model:** the `ContentEditable` surface is **uncontrolled**. Lexical
owns that DOM and reconciles it *itself*, outside React's render cycle. React is
only invoked to (re)render **DecoratorNodes** and whatever *you* choose to
subscribe to editor state. A keystroke mutates `EditorState` and Lexical patches
the DOM directly; the surrounding React tree does **not** re-render.

**How this build makes the difference observable:**

- Built with **NO virtualization** --- all statements render as real nodes. The
  hypothesis is that Lexical doesn't need it; a full transcript should stay
  responsive.
- A `LatencyMeter` plugin stamps `performance.now()` on each `beforeinput`
  (module-scoped `lastKeystrokeAt`) and measures the gap to the resulting
  `registerUpdateListener` callback. It renders `edits / last ms / max ms`.
- **The tell:** only the tiny `LatencyMeter` component re-renders per keystroke.
  Type into the Lexical editor and watch React DevTools --- the editor surface
  and the statement list do not re-render. Do the same in Slate and the element
  tree lights up. That contrast *is* the measurement.

**Verdict:** the controlled-vs-uncontrolled hypothesis is **confirmed by
construction** --- Lexical structurally cannot incur Slate's per-keystroke React
reconciliation of the transcript, because the transcript isn't React-rendered
after seed. The `LatencyMeter` lets the human put numbers on it: expect
single-digit-millisecond updates with virtualization **off**, on the same full
transcript where Slate needed it on. If a pathological transcript ever does drag,
`@tanstack/react-virtual` remains available --- but this build deliberately ships
without it, and the recommendation is that it won't be needed.

## Litmus test 2 --- SPLIT-ON-ENTER

**Slate's wall:** the user could not implement "split a statement on Enter" ---
Slate's `insertBreak` override is nearly undocumented (the abandoned
`wihCaptionSplit` / `insertBreak` seam in the Slate route is the scar tissue).

**How Lexical does it (`SplitStatementPlugin`):** a single `registerCommand`
against the public, typed `KEY_ENTER_COMMAND`:

- Registered at `COMMAND_PRIORITY_LOW` (value `1`). RichTextPlugin's default
  Enter handler sits at `COMMAND_PRIORITY_EDITOR` (value `0`). Lexical runs
  command handlers **high priority first** and stops at the first that returns
  `true`, so ours **pre-empts** the built-in paragraph/linebreak insert cleanly.
  No monkey-patching, no reaching into editor internals.
- Inside the handler (already in an editing context, so `$`-prefixed functions
  work): find the enclosing `StatementNode` via `$findMatchingParent`, compute the
  caret offset relative to the whole statement, slice text into `head`/`tail`,
  rewrite the current statement as `head`, and spill `tail` into a **new**
  `StatementNode` inserted after it, then `selectStart()` into the new node.

**API discoverability:** night and day versus Slate. "How do I run code on Enter?"
has one obvious, documented answer in Lexical --- `registerCommand(KEY_ENTER_COMMAND, ...)`
--- with an explicit, legible priority model for overriding defaults. This is the
single most decisive result of the spike: **the feature Slate blocked on took a
few dozen readable lines against a first-class API.**

**Backend gap (noted, not built):** the split is **client-side / visual-only**.
The backend exposes only `editStatement(uid, text)` --- no `splitStatement` or
`createStatement`. The new node therefore gets a **synthetic uid** (marked with
`"::split-"`), and the persistence seam **skips** any statement whose uid carries
that marker so it never fires a doomed `editStatement` for a row that doesn't
exist. To make splits durable, the backend needs a mutation along the lines of
`splitStatement(uid, atOffset)` (or `createStatement` + reindex) that mints a real
uid and rebalances `startTime`/`endTime`. Until then, split is a UI preview.

## Litmus test 3 --- REACT-IN-EDITOR (the primitive for graph tagging)

**Why it matters:** the user wants to *see* `EditorState` drive React --- a
mention/tag chip --- because that is exactly the primitive future graph-tagging
will need: an inline thing that lives in the document (serialises, undoes,
participates in selection) yet paints itself with arbitrary React.

**How it wires (`TagChipNode` + `TagChipPlugin` + `TagButton`):**

- `TagChipNode extends DecoratorNode<JSX.Element>`. Its `decorate()` method
  returns `<TagChip label={...} />`. **`decorate()` is the state -> React
  bridge**: @lexical/react's decorator machinery mounts whatever it returns into
  the editor DOM at the node's position and re-renders it when the node changes.
- The node is registered in `initialConfig.nodes`, so Lexical can construct,
  serialise (`exportJSON`/`importJSON`), and reconcile it like any built-in.
- Insertion goes through a typed command: `createCommand<string>()` mints
  `INSERT_TAG_CHIP_COMMAND`; `TagChipPlugin` registers the handler that does
  `selection.insertNodes([$createTagChipNode(label)])`; the out-of-editor
  `TagButton` just `dispatchCommand`s it. This decoupling --- toolbar button ->
  command token -> node mutation -> React re-render --- is the whole point.

**What it implies for graph tagging:** the path is clear and short. A future
`PersonMentionNode`/`TagNode` becomes a `DecoratorNode` whose `decorate()` renders
a real React component (autocomplete popover, avatar, link into the Neo4j graph),
whose `exportJSON` carries the graph uid, and which is inserted by a command wired
to a typeahead. The chip in this spike is that pattern in miniature, hard-wired to
a button instead of a typeahead. Crucially, this is **captions-first-safe**: it is
a human-invoked insertion (a button/command), not auto-LLM entity-tagging --- it
respects the product philosophy that ML stays a draft humans edit at their
discretion.

**Inline content vs. block chrome --- two different React seams.** A `DecoratorNode`
is the bridge for *inline content that flows with the text* (a chip mid-sentence).
Non-editable *block chrome* (the timestamps beside a statement) is a different need,
solved by `getDOMSlot` re-pointing the reconciler at an inner content element while a
`setDOMUnmanaged` sibling holds the chrome (see `StatementNode`). Today that chrome is
imperative DOM, but the same unmanaged subtree is a valid React portal target --- so
React-rendered block chrome (a speaker `<Select>`, a confidence meter) is a short
follow-on, not a rewrite. Between the two seams, Lexical covers both graph-tagging
shapes: inline mentions *and* per-statement metadata controls.

## The persistence porting seam (Slate op-stream -> Lexical dirty-nodes)

Worth calling out because it is the one place the two editors think differently.
Slate handed us an **operation stream**; the Slate route keys its debounce off
`operation.type.includes("text")` and walks to `Editor.parent`. Lexical has **no
operation stream** --- `registerUpdateListener` hands you **dirty node sets**
(`dirtyLeaves`, `dirtyElements`) per update. So `PersistencePlugin` inverts the
approach: map dirty nodes up to their `StatementNode` ancestors, dedupe by uid,
and fire a **per-uid** debounced `editStatement`. Per-uid debouncers (vs Slate's
single shared one) are strictly *more* correct --- rapid edits across two
statements no longer cancel each other's save. The seam is commented in place.

## Running discoverability / documentation log

Rated as I went, since the brief asked for a discoverability verdict, not just a
works/doesn't:

- **Commands & keybindings (test 2): excellent.** `createCommand`,
  `registerCommand`, the `COMMAND_PRIORITY_*` ladder, and `KEY_ENTER_COMMAND` are
  discoverable by name and consistently documented. This is the strongest contrast
  with Slate.
- **Custom nodes (`ElementNode`/`DecoratorNode`): good, with a learning curve.**
  The required static surface (`getType`/`clone`/`importJSON` + instance
  `createDOM`/`updateDOM`/`exportJSON`) is well documented and the failure mode
  for a missing registration is loud. `clone` copying every field *including the
  key* is the one non-obvious footgun; the getters-via-`getLatest()` idiom is
  learnable but not self-evident.
- **Non-editable block chrome (`getDOMSlot`): good, once discovered.** The
  timestamps are real chrome DOM --- the analogue of Slate's `contentEditable={false}`
  child. `createDOM` returns a wrapper (chrome column + content element),
  `getDOMSlot(element).withElement(content)` re-points the reconciler at the content
  element, and `setDOMUnmanaged` fences off the chrome so selection/reconciliation
  ignore it. `ElementDOMSlot.resolveLeafPosition` handles DOM-caret -> offset mapping
  for this wrap pattern, so selection needs no hand-rolled math. (An earlier draft of
  this node used a CSS `::before` fed by `data-label` and claimed a real child "would
  desync the reconciler" --- that was wrong: `getDOMSlot` is the supported path, and
  unlike a pseudo-element, real chrome scales past a text label to speaker
  `<Select>`s, confidence meters, and tag affordances.) `getDOMSlot` is
  `@experimental` in 0.48 but fits exactly; discoverable only once you know it
  exists --- worth writing down for the team.
- **`@lexical/react` plugin composition: excellent.** Every concern is a headless
  component that grabs the editor via `useLexicalComposerContext` and registers in
  an effect. The route reads as a list of capabilities.
- **`@lexical/utils` (`$findMatchingParent`, `mergeRegister`): good** --- exactly
  the helpers you reach for, discoverable via the package's exports.
- **Seeding & the "seed" tag: good.** `editor.update(fn, { tag: "seed" })` plus
  `tags.has("seed")` in listeners is the clean, documented way to distinguish a
  synthetic build from a human edit. Without it the seed would fire N spurious
  `editStatement` calls on mount.
- **Docs overall:** materially better than Slate. Slate's core is famously
  under-documented (the abandoned `insertBreak` seam is proof); Lexical's API is
  large but the naming is honest and the guides cover the exact tasks this spike
  needed. A couple of things (the `getDOMSlot` slot-redirection pattern for chrome,
  `getLatest()` in getters) are tribal knowledge worth writing down internally.

## Recommendation: MOVE TO LEXICAL

- **Latency (test 1):** the architecture eliminates Slate's per-keystroke React
  reconciliation of the transcript by construction; this build runs the full
  transcript with virtualization **off**. Confirm with the built-in `LatencyMeter`.
- **Split-on-Enter (test 2):** the feature Slate could not deliver is a few dozen
  readable lines against a first-class, documented command API. Decisive.
- **React-in-editor (test 3):** `DecoratorNode.decorate()` gives a clean, short,
  captions-first-safe path to graph-tagging chips.
- **Discoverability:** consistently better than Slate across every surface the
  spike touched.

**Blocking follow-up before shipping split durability:** add a backend
`splitStatement` (or `createStatement` + reindex) mutation so split products get
real uids and time windows; today they are visual-only and deliberately excluded
from persistence.

**Suggested next steps if adopting:** (1) port the playhead-follow auto-scroll
(intentionally omitted here --- the spike focused on the three litmus tests);
(2) decide whether `@tanstack/react-virtual` is ever needed under real transcript
sizes (expected: no); (3) design the `splitStatement` mutation and the
optimistic-concurrency story (the existing `oldHash`/`newHash` ack path) for split
products.
